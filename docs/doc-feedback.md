# Documentation feedback: Azure DNS Private Resolver regional failover

Suggested improvements for Microsoft Learn, based on gaps found while building this lab. Each item lists the affected page, the gap, the evidence and a proposed change.

| # | Page | Gap | Evidence | Suggested change |
|---|---|---|---|---|
| 1 | [Tutorial: resolver failover](https://learn.microsoft.com/azure/dns/tutorial-dns-private-resolver-failover) | Covers only on-premises forwarders. There is no guidance for **Azure VMs** in spoke VNets. | Designs A–D in this lab behave very differently (29–100 % success during an IE outage). | Add an "Azure workloads" section comparing VNet custom DNS `[IE r1, IE r2]` with multi-target forwarding rules. |
| 2 | [Endpoints and rulesets](https://learn.microsoft.com/azure/dns/private-resolver-endpoints-rulesets#dns-forwarding-rulesets) | The exponential backoff on targets is mentioned, but its effect on **failback** isn't. | Measured: traffic stays on the secondary target ≈ 144–173 s after the primary recovers. | Document typical failover/failback behaviour, or state that failback timing isn't guaranteed. |
| 3 | [Reliability in DNS Private Resolver](https://learn.microsoft.com/azure/reliability/reliability-dns-private-resolver) | No guidance on client-side design for multi-region resilience, or on the fate-sharing between a ruleset and its outbound endpoint's region. | Ruleset links are same-region only (cited); a design-D rule in r1 can't survive loss of the r1 resolver. | Add a "client patterns" table and call out per-region rulesets. |
| 4 | [Name resolution for VMs – DNS client configuration](https://learn.microsoft.com/azure/virtual-network/virtual-networks-name-resolution-for-vms-and-role-instances#dns-client-configuration) | No warning that an NXDOMAIN from the first server stops the client from trying later servers. | F6: Design C success fell to 5–38 % while the second server (IE r2) was healthy. | Add a note: list only servers that return identical answers, and don't combine 168.63.129.16 with custom resolvers as a failover pair. |
| 5 | [DNS Private Resolver overview](https://learn.microsoft.com/azure/dns/dns-private-resolver-overview) | It isn't stated whether NSGs/UDRs on the delegated inbound/outbound subnets are enforced. | Measured: NSG deny on 53 and UDR black holes take effect within seconds (F1a, F1c, F2). | State the supported behaviour, and recommend (or advise against) NSG-based failover drills. |
| 6 | Any failover page | No guidance on how to **test** resolver failover safely. | NSG deny on the inbound-endpoint subnet is a reversible, low-risk drill in this lab. | Add a "Test your failover" section. |
| 7 | [Troubleshoot Azure DNS](https://learn.microsoft.com/azure/dns/dns-troubleshoot) / conditional-forwarder troubleshooting | These pages list an NSG outbound deny on port 53 as a cause of failed resolution. In our test, an outbound deny on the **client** subnet to the inbound endpoint was **not** enforced. | F1b: the rule (priority 100, `*`, IE r1/32, port 53) appeared in the NIC's effective rules, yet UDP and TCP `dig @IE-r1` from that VM kept succeeding (100 %). An inbound deny on the endpoint subnet (F1a) worked. | Clarify where NSG rules are and aren't enforced for traffic to resolver endpoints. |
| 8 | [Name resolution for VMs](https://learn.microsoft.com/azure/virtual-network/virtual-networks-name-resolution-for-vms-and-role-instances) | No note that UDP-only loss isn't recovered by TCP. | F5u: with only UDP/53 blocked, direct queries succeeded 0–1 %; clients timed out rather than retrying over TCP. | Note that TCP fallback needs a truncated response, so a UDP-only block behaves like a full outage. |
